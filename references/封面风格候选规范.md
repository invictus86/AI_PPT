# 封面风格候选规范

> 当前1.2.0：三步基础流程见《阶段流程.md》。第一步规划经主控深度审阅可生成四封面，用户选封面并授权试做时才确认规划；第三步实际全稿由主控验收锁定，不新增PDF用户审批。主题活动内容与配套优先遵循《主题班会与家长会深度二创规范.md》《主题活动教案与会议实施方案规范.md》。

本文只规定阶段2A四张封面候选、用户选择、`deck_style.json` / `layout_intent.json` 沉淀，以及已选封面质量通过后的转正。全部封面文字（包括副文、编号、页码和图注）均来自阶段1该页`final_visible_text`，不能按候选风格另造文案。上游风格来源见 [图片风格与提示词交付规范.md](图片风格与提示词交付规范.md)，final prompt 编译见 [提示词建设规范.md](提示词建设规范.md)，路线和证据见 [生图证据链.md](生图证据链.md)。

## 目标

阶段2正式生成全套整页图片并打包图片版 PDF 前，先基于阶段1 `design_contract.json` 生成四张媒介、质感或视觉表达实质不同的封面图，让用户选择整套 PPT 的视觉方向。

这是固定流程。除非用户明确说“你直接替我选”，否则主控大模型不能跳过用户选择，也不能让 runtime 自动选择。

## 触发时机

进入阶段2后先做阶段2A：

```text
阶段2A_封面风格候选
-> 用户选择风格
-> 锁定 deck_style 和 layout_intent
-> 选中且质量通过的封面候选直接转正为正式封面页
-> 阶段2B_全套整页图片与图片版 PDF
```

阶段2A 仍属于阶段2，不新增用户阶段目录。

## style card

四张封面候选在生成前，主控大模型必须为每个候选写 style card：

```text
_state/阶段2/cover_options/style_cards/cover_option_A.json
_state/阶段2/cover_options/style_cards/cover_option_B.json
_state/阶段2/cover_options/style_cards/cover_option_C.json
_state/阶段2/cover_options/style_cards/cover_option_D.json
```

建议结构：

```json
{
  "schema_version": "1.0",
  "option_id": "A",
  "basis_design_contract": "_state/阶段1/design_contract.json",
  "style_positioning": "",
  "best_for": [],
  "composition": "",
  "visual_medium": "",
  "palette_strategy": "",
  "typography_direction": "",
  "layout_extension": {
    "cover_to_inner_pages": "",
    "suitable_page_roles": [],
    "risky_page_roles": []
  },
  "risk_notes": [],
  "prompt_constraints": [],
  "selection_explanation": ""
}
```

style card 放 `_state/`，不放用户可见目录。用户查看封面图片和成功图片的实际提示词；候选差异、适用场景、内页延展和风险由主控在回复中说明或写入同一份 `图片生成提示词.md`，不另建独立封面选择文档。

每个待生成候选还须准备 `image_prompt_plan`，字段与 [提示词建设规范.md](提示词建设规范.md) 一致。使用 `record-image-prompt-plan --option-id A` 等对应命令，先保存到 `design_contract.stage2_cover_option_strategy.option_briefs` 中的候选，派发时同步到style card；只手改派发后的卡片不能更新来源。主控归并本候选独立媒介、配色、字体、构图和共用适龄/真实安全限制。候选默认不显示页码；用户明确启用且已确认policy.applies_to包含cover时，候选与正式封面按相同policy单独编译一次。派发不能把共同风格全文复制到媒介、配色、字体字段，也不能覆盖仍然有效的候选约束。

## 四张封面要求

四张封面必须：

- 只允许由 `openai_image_api` 中转路线的 `gpt-image-2.5` 分组生成，按同一个 `execution_group` 建 batch manifest，并记录对应 evidence、结果 ID 和图片 sha。分组不可用或失败时停止并报告；主控不得改用其他分组、模型、中转站或内置 `image_gen`，普通继续/重试指令不解除限制。
- 默认目标尺寸为 16:9 `1672x941` 的 1K 级画布，允许生成器返回存在轻微尺寸差异；优先底线为 `1600x900`，尽量保留生成返回的原始 raster，不主动把封面候选压缩、降采样或另存为更小图。
- 使用同一个 PPT 主题和标题语义。
- 都是完整中文封面图。
- A-D分别明确媒介、质感或视觉表达，须实质不同；共享主题、批准文字、适龄与真实安全要求。选定后才统一全稿媒介、配色和字体。
- 都能扩展成整套 PPT 的视觉系统。
- 不出现英文占位、乱码、假字、伪文字。
- 每张封面必须绑定对应 style card。
- 每张封面必须使用 `页面规划.md` / `content.json` 中确认过的封面最终可见中文文字。

建议差异维度：

- 构图：中心主视觉、左文右图、全景沉浸、抽象概念。
- 视觉重点：突出标题、主视觉、场景或信息关系，体现本候选独立质感。
- 大小关系：标题与主视觉占比、主体与留白关系；必要页面文字完整呈现。

## 用户可见产物

放在：

```text
阶段2_图片版PPT/封面风格候选/
```

建议文件：

```text
cover_option_A.png
cover_option_B.png
cover_option_C.png
cover_option_D.png
```

用户查看封面图和同一份 `图片生成提示词.md`；候选 A-D 的差异、适用讲述方式、内页延展、风险和主控建议由主控在对话里说明，style card、packet、hash、provider JSON 仍留内部。

## 运行过程文件

放在：

```text
_state/阶段2/cover_options/
  packets/
  prompts/
  results/
  style_cards/
  batches/
  api_calls/ 或 image_gen_calls/
  api_outputs/ 或 image_gen_outputs/
  api_batch_runs/
  selection/
```

其中：

- `packets/` 放生图任务包，包含 `image_generation_route`。
- `prompts/` 放四张封面的 final prompt。
- `results/` 放 provider 路线、证据和结果记录。
- `results/` 还必须记录实际尺寸、目标尺寸、目标容差、偏好底线、`meets_target_size`、`meets_preferred_size` 和 `size_warnings`。
- `style_cards/` 放四张候选的设计策展资产。
- `selection/` 放用户选择记录。

## 用户选择后

用户选择一个封面方向后，主控大模型必须沉淀：

```text
_state/阶段2/deck_style.json
_state/阶段2/layout_intent.json
```

`deck_style.json` 记录视觉系统。

`layout_intent.json` 记录版式意图和全局布局规则。

没有用户选择和这两份主控资产，不进入全套整页图片生成。

如果选中封面候选的中文文字、构图、证据链和 canonical 策略都通过主控检查，默认直接将该图转正为阶段2正式封面页，不再二次生成：

```text
阶段2_图片版PPT/img/slide_XXX.png
_state/阶段2/results/slide_XXX.json
```

转正后的正式 result 必须是 `purpose=full_slide`，并保留原 `cover_option` 的 `image_generation_route`、对应结果 ID、对应 evidence path、`parallel_batch_path`、`image_sha256`，额外记录：

```json
{
  "promoted_from_cover_option": true,
  "selected_cover_option": "A",
  "cover_option_result_path": "_state/阶段2/cover_options/results/cover_option_A.json",
  "cover_option_image_path": "阶段2_图片版PPT/封面风格候选/cover_option_A.png"
}
```

只有以下情况才重做封面：用户明确要求“风格可以但封面重做/微调”，或主控 QA 发现选中候选有乱码、伪字、文字与阶段1不一致、重要构图错误、证据链缺失、尺寸策略不可追溯、低于 `1600x900` 优先底线且主控判断会影响观感等问题。

## prompt 输入

主控准备候选画面计划时核对：

- 阶段1封面页最终可见中文文字。
- `design_contract.json` 的路线、受众、审美意图和封面候选策略，转成适用的具体画面要求。
- 对应 `style_card` 的构图、媒介、色彩、字体和风险约束。
- 当前适用的通用审美要求和禁止项，不回流已经过期的默认限制。

正式prompt仅编译本候选的完整画面计划和批准正文。只写本张构图，不写“四张需要不同”等整批安排；通用封面规划中冲突的位置要求先由主控解决，不能再追加另一套位置。系统开头仅写横版中文PPT封面，尺寸由接口参数设置，不往prompt添加像素尺寸、数字画幅比例或清晰度等级。

旧项目可按原资产只读恢复；要发起新请求时，先补齐当前设计依据和候选画面计划，不靠旧A—D fallback猜测新要求。

## 禁止事项

- 不让 runtime 自动选择封面。
- 不把四张封面候选整组直接打进图片版 PDF。
- 不把未选中的封面候选转正为正式页面。
- 不在选中封面已质量通过时，为进入阶段2B而默认二次生成封面。
- 不用本地渲染、fixture、source replay 冒充正式封面。
- 不改用本地渲染、浏览器截图、旧图复制、ImageGen/image2 或内置 `image_gen`；正式新请求只能使用中转 API 的 `gpt-image-2.5`。
- 不把四张封面整组无batch manifest地随意生成；中转API路线同组并发，单个batch/run最多6，多个独立批次不共享额度、不设全局生图互斥。返回未知先核对证据，不能盲目重提。
- 封面候选生成成功后，实际完整提示词与对应图片写入阶段2根目录 `图片生成提示词.md`；失败请求仅留内部，参考来源说明放在prompt代码块外，历史成功快照不改写。
- 不把 style card 放进用户可见目录。
- 不因为某张封面好看就忽略用户选择。
- 不让封面候选新增 `final_visible_text` 之外的标题、副标题、英文标签或装饰性文字。
