# 生图证据链

本文只规定阶段2正式生图路线、packet、batch、evidence、result、hash、尺寸、比例、并发和历史请求处理。上游风格来源见 [图片风格与提示词交付规范.md](图片风格与提示词交付规范.md)，final prompt 编译见 [提示词建设规范.md](提示词建设规范.md)，封面候选选择见 [封面风格候选规范.md](封面风格候选规范.md)。

证据链证明图片从哪里来、用什么提示词生成、是否有真实结果和尺寸事实；它不负责审美判断，也不替代用户确认。

## 正式路线

阶段2封面风格候选、阶段2B试样、全套整页图片及返工请求，先按下节读取生图模式。`native`直接调用当前聊天内置生图工具，不尝试中转、不要求中转故障证据；`auto`优先使用 `openai_image_api`；中转模型/分组仍只允许精确值 `gpt-image-2.5`。明确中转故障且无可恢复结果时，允许接续下文规定的GPT原生备用 `codex_image_gen`，不增加用户授权节点。

中转禁止使用 `gpt-image-2-vip`、`gpt-image-2.5-sunburst`、`gpt-image-2.5-flare` 或任何其他模型/分组，参数、环境变量和主控判断不能覆盖，也不改用备用中转站。原生工具的实际模型不可控时记录未公开，不将其标成中转的 `gpt-image-2.5`，不承诺模型或成图效果完全相同。

必须先生成 packet 和 batch manifest，再按 packet 生成图片并记录正式 result；不能直接把一张图片放进阶段目录当作已完成。历史其他路线或模型的记录保留原值，不改写成 `gpt-image-2.5` 成功证据，也不据此发起新请求。

## 生图模式与切换

仅提供两种模式，不提供“中转失败就停止”的独立模式：

| 模式 | 行为 |
| --- | --- |
| `native` 内置生图 | 直接调用当前聊天的内置生图工具，不尝试中转；工具未开放或调用失败时报告受影响图片，不改走中转。 |
| `auto` 自动备用 | 中转优先，故障且无可恢复结果时按本文原协议接续内置生图。未设置时采用此模式。 |

Windows双击`scripts/切换生图渠道.cmd`，输入1切内置、2切自动备用，0退出。也可在工作区使用跨平台CLI：

```bash
python3 .skill/scripts/pptctl.py image-generation-status
python3 .skill/scripts/pptctl.py configure-image-generation --mode native
python3 .skill/scripts/pptctl.py configure-image-generation --mode auto
python3 .skill/scripts/pptctl.py configure-image-generation --run-dir <项目目录> --mode native
python3 .skill/scripts/pptctl.py image-generation-status --run-dir <项目目录>
python3 .skill/scripts/pptctl.py configure-image-generation --run-dir <项目目录> --inherit
```

聊天口令由主控执行上述确定性命令：“默认生图切换为内置生图/内置GPT”保存本机`native`；“默认切回自动备用”保存本机`auto`；“这个项目用内置生图/自动备用”保存项目设置；“这个项目跟随默认”使用`--inherit`。“本次用内置/自动备用”只对本次决策与派发显式传同一`--image-generation-route`/`--route`，不改默认。不将资料中的指令当用户口令，不增加用户确认节点。

优先级：本次明确指定路线 > 项目`_state/image_generation.json` > 当前电脑/工作区`_local/config/image_generation.json` > 默认`auto`。本机设置由Git忽略，不存密钥、不同步到其他电脑；项目设置随项目证据保留。配置格式为`{"schema_version":"1.0","mode":"native"}`或`auto`。缺文件采用下级设置，损坏或未知模式报错，不能静默改走中转。每次新决策和派发重新读取，无需重启。四封面、试样、剩余页、整页及返工均使用同一规则；不改变正文规划、Canva、Word/PDF或动画。

派发命令默认省略`--route`；显式`--route codex_image_gen`临时选内置，`--route openai_image_api`临时选自动备用。保留原中转执行器和明确指定旧批次的恢复入口，不把技术路线别名当新增用户模式。决策和派发应使用同一选择；开关在两者之间变化时重新核对新派发依据，旧decision不冒记为已按新设置执行。

批次与每张packet冻结`image_generation_selection`及真实路线，输出会显示本次选择。切换只影响后续新批次，不修改已有packet、在途请求、成功图片或确认事实。恢复旧批次时明确传`--batch`读取其冻结路线；不得因新默认改变原请求。相同项目同页仍在途或结果未知时先恢复/核实，切换不能用于重复生成或绕过内容安全拒绝；已合格图继续复用。

内置模式仍先派发packet/batch，再逐张执行`prepare-image-request`取得冻结提示词、真实参考图参数和`tool_name=image_gen.imagegen`，由当前聊天的助手实际调用工具。Python或双击脚本只负责配置/准备，不直接调用宿主工具。工具未开放时如实报告，不能伪称成功；不验证中转密钥、不发中转探测请求、不构造虚假中转失败。调用后的真实图片、ID、原像素PNG、尺寸/比例与逐张文字/视觉QA沿用下文第3—7步；`model/size/quality/output_format`未开放则如实记未显式设置，不承诺两路线模型或效果相同。

## 强制模型与失败处理（仅自动备用）

执行规则：

- 首先派发 `openai_image_api` / `gpt-image-2.5` 请求，不设置其他中转分组或备用模型。
- 用户明确说“走中转 API / 用 API / 用苍原 / 国内直连 / 用 `openai_image_api`”时，本次使用自动备用的 `openai_image_api` 首选路线；普通“默认路线”读取当前本机/项目设置，不硬编码中转。
- 未配置中转密钥且没有旧在途请求时，可以直接准备原生备用。明确的鉴权、接口不存在或限流拒绝，以及明确模型不可用的响应，可为受影响图片交接原生工具。超时、断线、SSL EOF、服务异常或进程中断后获取不到返回图片，且本地无可恢复图片、可用返回链接或可查询任务编号时，直接判定本次生图失败，由主控自行登记并重试或交接原生GPT，不暂停请用户判断。
- 先一次性检查当前请求的 `request_results`、API输出/evidence和实际图片；已有图片或可用返回链接时先恢复，有可查询任务编号时先查询原任务，仍在途不重发。中断且无上述恢复线索即可按交付失败处理，不要求证明服务端从未生成，不要求用户查中转后台、确认费用或批准重复计费；仅等待较久而请求仍运行不算中断。返回损坏或下载失败时仍先尝试恢复已有结果。
- 中断请求若仍记为 `unknown` / `submitted` 等受保护状态，主控自行执行 `resolve-image-request --request-key <键> --evidence <JSON>`，证据含 `controller_reviewed=true`、`resolution=confirmed_no_result` 和具体 `reason`（实际中断错误、本地结果检查及缺少恢复线索的事实）。这里的无结果指无可恢复交付图片，`controller_reviewed` 是主控核实，不是用户确认。保留原失败和已知计量，未知费用如实留空，不将生图失败写成未计费。
- 解除该请求保护后，可同一路线重试一次，也可直接执行 `prepare-native-fallback` 使用原生GPT；同路线重试仍失败且无可恢复结果时，优先交接原生GPT，避免无限付费重试。原生工具不可用或失败时按原规则报告受影响图片，其他已授权且可完成的工作继续。
- 内容安全拒绝不得改渠道规避。其他未被自动识别的中转故障，主控提供核实证据再用 `prepare-native-fallback`；证据不能覆盖仍在途或已有可恢复结果的请求。普通“继续”“重试”不放宽中转模型规则。
- runtime 在配置加载、批次预检、请求准备及发送参数校验时拒绝其他模型/分组；命令行 `--model` 只接受 `gpt-image-2.5`。冲突配置必须报错，不得悄悄覆盖或按其他分组发请求。

同一中转批次不混用其他中转模型/分组。备用图片建立独立原生子批次，保留原中转快照和失败事实；最终全套可复用合格中转图并接续原生图，不能把失败API packet手工补成成功。原批次已交接的图片不再由中转执行器重发。

## 尺寸和清晰度策略

阶段2正式图片默认目标尺寸：

```text
1672x941
```

这是 16:9 的 1K 级默认目标。生成器实际返回可能存在轻微尺寸差异；轻微差异本身不是质量风险，但必须如实记录实际宽高、目标尺寸、容差和是否落在目标容差内。`1600x900` 是当前优先底线，低于该底线时作为清晰度风险记录，由主控按实际效果决定继续、在同一分组重试或停止报告；不得切换分组或路线。

统一规则：

- 中转尺寸通过接口参数设置；原生工具未开放尺寸参数时保留同一目标并记录未显式设置。实际宽高、比例和清晰度分别核验。新prompt只描述横版画面，不自动加入像素尺寸、数字画幅比例或1K/2K/4K指令；批准正文中的尺寸知识原样保留。
- packet 必须写入 `target_size=1672x941`、`preferred_minimum_size={width_px:1600,height_px:900}`、`target_size_tolerance_px` 和 `size_policy=preserve_generated_raster_no_downscale`。
- result 必须记录实际 `width_px`、`height_px`、`target_size`、`preferred_minimum_size`、`target_size_tolerance_px`、`meets_target_size`、`meets_preferred_size` 和 `size_warnings`。
- 新阶段2封面候选、试样和正式页面图，两条路线均只使用 `preserve_api_raster`，保持生成器返回的原始像素和原图字节；不缩放、裁切、补边或重新编码后作为正式图，不以warning代替这一要求。
- 历史 `normalize_at_stage2`、`postprocess` 与降采样warning继续按原事实读取，不自动重写记录或撤销已有确认；它们不再是新正式图入账入口。PDF保持原页面尺寸和居中放置规则，以页面坐标安排图像大小，内部嵌入原始像素，不先降采样成页面位图；原图及页面PNG不变。
- 如果返回低于 `1600x900`，不要本地拉伸冒充 1K 级结果；应保留真实返回尺寸并记录 `meets_preferred_size=false` 和 `size_warnings`，主控可按实际清晰度决定继续、在同一 `gpt-image-2.5` 分组重试提示词或停止报告。
- 如果 `gpt-image-2.5` 无法稳定返回 1K 级结果，可以按实际质量决定继续，但阶段决策或对用户说明里应提醒这是低于优先底线的结果；不得因此更换分组或路线。

比例与像素宽高分别验收。目标比例为 `16:9`，按实际图片宽高计算相对误差 `abs((width/height)/(16/9)-1)`；默认相对比例容差为 **2%（0.02，包含边界）**。它与宽、高各自的像素容差无关，不能因为达到最低宽高就判定比例通过。

新结果同时记录 `target_aspect_ratio`、`aspect_ratio_error`、`aspect_ratio_tolerance` 和 `meets_target_aspect_ratio`。偏差超过2%时保留原图，记录比例warning，由主控核对后决定返工或有依据地接纳；不得自动拉伸或裁切。旧结果没有这些字段时可读取实际图片只读核算，不伪造原记录，也不自动撤销已有确认。以上比例和尺寸数据留内部验收，不追加到prompt。

## GPT原生生图备用路线

Python执行器不能直接调用宿主工具：它只准备原生任务并返回 `awaiting_native_image_generation`。主控必须实际调用当前宿主 `image_gen.imagegen`，不能将任务准备成功当作生图成功。宿主工具未提供时报告受影响图片，不替换成第三方模型或本地渲染。

1. 原三步仍正常派发中转批次。`run-image-api-batch` 在明确拒绝后自动返回 `native_fallback.packet_paths`；未配置中转密钥时也交接，但仍检查旧请求。合格结果复用，不扩大原授权范围。
2. 对已核实、未被自动识别的中转故障执行：`prepare-native-fallback --run-dir <项目目录> --batch <原批次> --evidence-file <核实证据JSON>`。证据须包含 `controller_reviewed=true`、`relay_unavailable=true`、`resolution=confirmed_no_result` 和具体 `reason`。中断且无可用恢复线索的请求，先由主控按上文自行执行 `resolve-image-request`，再交接；不得将这一步转为用户查后台或人工判断。这属于主控核实，不是新增用户确认。
3. 对每个原生packet执行 `prepare-image-request --run-dir <项目目录> --packet <原生packet>`。返回不可变 `packet_path`、逐字相同的 `prompt`、`tool_name`、可实际提交的 `tool_arguments`、`requested_parameters` 和未开放参数清单。同一原生请求准备后结果未知时不重复调用，应先恢复原工具结果；工具失败则停止该图片并如实说明，不自动重试。
4. 有参考图片时，先实际查看，再用返回的 `referenced_image_paths` 作为真实输入；不丢弃原参考图或改变顺序。原中转仅保存远程图片URL、尚无可核对本地图时先补齐同一图片，不静默省略。提示词不因路线改变而重新编译、删减、追加尺寸指令或改写正文。
5. 调用原生工具时只传 `tool_arguments` 中实际支持的字段。默认目标 `1672x941`、16:9、原像素/比例容差、`1600x900`优先底线、已批准更高尺寸、high和无损PNG要求全部保留。原生工具未开放 `model/size/quality/output_format` 时，这些仅是要求而非已设置参数；不伪造实际模型或参数，按真实图片逐张检查文字、像素、比例、清晰度和视觉一致性。原生结果必须真实PNG并保持原始raster，不通过缩放、裁切、拉伸或改后缀冒充达标。
6. 输出复制到项目内部，使用返回的冻结 `packet_path` 执行原有 `record-image-result`，`provider/source=codex_image_gen`，填写真实可取得的 `generation_id/tool_call_id/image_gen_result_id`。缺少真实调用标识时保留图片并报告证据缺项，不编造ID；正常生成 `image_gen_evidence_path`、图片sha、批次记录和尺寸事实。不能填写假的中转API evidence，也不能沿用原API成功标识。
7. 原生结果继续进入原封面候选、试样或正式 `full_slide` 位置，沿用原PDF打包、内容/视觉QA、选封面及前5页确认流程。每个子批次最多6并发；不同批次和窗口继续独立，不设置全局生图锁。历史其他路线记录保留原事实，不改写既有图片或用户确认。

## OpenAI Image API 中转路线

中转 API 路线使用 OpenAI-compatible batch runner，是自动备用模式的首选路线；内置模式不调用本节执行器。

默认配置：

- 中转站入口：`https://k.grsai.com/`
- 实际 API `base_url`：`https://eb.grsaiapi.com/`
- 生成端点：`/v1/images/generations`
- API key：优先从环境变量 `PPT_IMAGE_API_KEY` 读取；没有环境变量时读取本机密钥文件 `~/.codex/secrets/ppt-skill-v3/image_api_key`，也可通过 `PPT_IMAGE_API_KEY_FILE` 指定其他本机密钥文件。密钥不能写入 Skill 文档、项目产物、batch 或日志。
- 模型/分组：固定 `gpt-image-2.5`，不是可覆盖的默认值。
- 默认尺寸：`1672x941`
- 默认质量：`high`
- 默认输出格式：`png`
- 默认响应格式：`b64_json`
- 单次生图任务超时：`500s`，覆盖 API 请求、响应解析和返回图片 URL 下载。
- 单个 batch/run 同组最大并发：`6`；多个独立 batch 可以由主控同时运行，不设全局互斥。
- 新默认路线要求请求体显式发送 `response_format=b64_json`，runner 直接保存返回的 base64 图片；只有兼容网关返回公网图片 URL 时，才写入 evidence/result 的 `provider_image_url`。

首次使用可先配置一次本机密钥文件：

```bash
python3 .skill/scripts/pptctl.py configure-image-api-key --stdin
python3 .skill/scripts/pptctl.py image-api-key-status
```

派发和执行：

```bash
python3 .skill/scripts/pptctl.py dispatch-cover-options --run-dir <项目目录>
python3 .skill/scripts/pptctl.py dispatch-stage2-trial-first5 --run-dir <项目目录>
python3 .skill/scripts/pptctl.py dispatch-stage2-remaining --run-dir <项目目录>

python3 .skill/scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage cover-options
python3 .skill/scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage stage2-trial-first5
python3 .skill/scripts/pptctl.py run-image-api-batch --run-dir <项目目录> --stage stage2-remaining
```

`--stage stage2` 只用于主控明确决定跳过试样时运行全套正式整页图片；新流程主路径是 `stage2-trial-first5` 通过后再运行 `stage2-remaining`。


`tool_call_id` 和 `image_gen_result_id` 可作为兼容字段保留，但中转路线的正式判断以 `api_call_id`、`image_api_result_id` 和 `api_evidence_path` 为准。

生产模式下，`api_evidence_path` 必须指向项目 `_state/` 内真实存在的 API evidence JSON，且其中的 `packet_id`、`api_call_id`、`image_api_result_id`、`api_endpoint`、`model`、`image_sha256` 和 `http_status=200` 必须与图片结果一致。新默认 `/v1/images/generations` 路线还必须校验 `response_format=b64_json`；旧 `/v1/draw/completions` 历史记录允许没有该字段。不能只手工填写几个 ID 冒充 API 调用。

历史Grsai解析工具只作为旧证据识别工具留存，不用于恢复旧项目或绕过新workflow和内容验收。当前正式生图使用项目有效的中转API配置；旧接口记录不能作为新请求成功的替代证据。

## Batch 与并发

所有正式生图都必须有 batch manifest：

- 封面候选：`_state/阶段2/cover_options/batches/<execution_group_id>.json`
- 阶段2B试样：`_state/阶段2/trial_first5/batches/<execution_group_id>.json`
- 阶段2正式图片：
  - `codex_image_gen`：`_state/阶段2/image_gen_batches/<execution_group_id>.json`
  - `openai_image_api`：`_state/阶段2/image_api_batches/<execution_group_id>.json`

每个新 batch 只有这一份可变、权威 manifest，记录成员、当前进度、状态和关联 ID；不再为每次更新写完整 `history/` snapshot。历史由冻结请求、路线 evidence、正式结果和决策/事件重建；旧项目的 history snapshot 继续可读，不自动迁移或删除。
中转 API 路线必须并发生成：

- 阶段2A四张封面候选作为同一个 `execution_group` 并发运行图片API批量执行器。
- 阶段2B试样作为独立 `execution_group` 并发运行；默认总共5页确认范围，包含已选封面，通常新增4张内页；选中封面直接转正复用，不再进入试样batch。
- 阶段2B试样通过后的剩余图片页按packet的 `execution_group` 并发运行，单个batch/run最多6；多个独立批次不共享额度、不设全局生图互斥。并发形式不替代质量验收。
历史官方路线的 batch、packet、evidence 和 result 保留用于只读核对，不允许据此提交新请求。

## 证据归属与图片去重

- 冻结请求是实际提交的提示词、参数、输入引用和请求身份的唯一事实来源。
- 路线 evidence 保存提供方返回、调用 ID、状态和必要原始信息；正式 result 保存最终采用页面、图片 SHA、尺寸、质量结论及两者关联。
- 成图以 SHA 在 `_state/阶段2/prompt_history/result_images/` 保留一份不可变内部证据；页面采用入口优先硬链接，无法链接时才单次复制。提示词历史和轻量 attempt 只能保存路径、SHA 和关联 ID，不能再另存同一图片或完整 result 镜像。
- 新项目不写 `result_receipts`；旧 receipt、旧完整 ledger 和 batch history 只读兼容。

## 图片用途

正式图片用途分三类：

- `cover_option`：阶段2A四张封面候选；用户选中且质量通过的候选可直接转正为封面页 `full_slide`。
- `trial_first5`：阶段2B试样图，供用户确认视觉、文字、密度和风格方向；内部名称沿用历史标识；默认总共5页，包含已选封面，短项目按实际页数。
- `full_slide`：阶段2B正式整页页面图，后续打包为图片版 PDF。
- `stage2_text_removed_background` / `stage3_background`：旧阶段3无字背景相关 purpose，只作为 legacy 识别，不作为新的正式 production 路线。

封面候选不能整组进入阶段2正式页面图，未选中的候选永远不能进入图片版 PDF。用户选中且主控检查通过的封面候选应直接 promotion 为正式 `full_slide` 封面结果，避免阶段2B重复生图。试样必须经用户确认和 runtime promotion 后，才能进入正式 `full_slide` results；已由封面候选转正的页面不再进入试样生图 packet。用户确认通过的试样页默认复用为正式页面，不为生成全套图片而重生。图片版 PDF 只使用 `full_slide`。

## Canonical 图片策略

请求尺寸不等于最终返回文件一定是该像素尺寸。新阶段2结果统一保留原图：

- `preserve_api_raster`：阶段2确认图保留实际生成返回尺寸。字段名沿用历史命名，也适用于 `codex_image_gen`。
- `normalize_at_stage2`：仅作为历史结果的识别值保留，不用于新正式结果。CLI旧参数仍可给出明确拒绝，不通过另设尺寸或方法绕过原像素要求。

新正式 `image_result.image_path` 指向原始输出的字节一致副本，源图、内部证据副本及页面图指纹一致；实际尺寸和比例仍独立验收，不靠处理图片满足目标。旧结果中的 `original_api_output`、`postprocess.manifest_path`、原图与canonical图指纹、尺寸和方法保持原样；历史读取及已有效结果复用不等于允许新图归一化，也不触发旧课件重制。

## 提示词要求

- 依照 [提示词建设规范.md](提示词建设规范.md) 编译有效的 `image_prompt_plan`，正文仅来自批准的 `content.final_visible_text`，保留专业术语、数字、单位和换行。
- 不新增英文占位、乱码或伪文字；不额外加入内部标题、页序或说明性编号。页码必须已在阶段1本页final_visible_text中，经text_roles.page_number引用；policy只安排一次位置/样式，不产生新数字。
- 每页提示词包含本页构图、主视觉、完整当前风格、具体文字布局和必要禁用项；页面目的、资料来源、执行说明和内部字段留在规划或台账。
- 封面候选分别明确独立媒介、质感或视觉表达，不能仅变配色/构图；共享批准文字与适龄/真实安全限制，单张请求只包含自身完整要求。
- 试样和正式图片使用相同的当前风格及适用deck/layout组件，主控先归并到计划，编译后不再追加原始组件。
- 新请求冻结前核对计划、实际prompt及摘要。旧待发包重新准备，已在途及成功历史快照不改写；成功文档逐字保留实际prompt，参考来源说明在代码块外。

用户可读 `阶段2_图片版PPT/图片生成提示词.md` 不在每张图片返回时重建。四张封面完成、五页试样完成、剩余页完成以及显式刷新/导出时必须完整刷新；任何交用户确认的节点都必须使用最新文档。

真实编辑接口使用的本地输入图，在准备请求时冻结到 `_state/阶段2/prompt_history/input_images/`，记录原始路径、归档路径和内容hash。API和原生备用提交使用同一归档输入，原输入随后变化不影响在途请求；归档文件本身被改动时不能继续提交。历史输入存档保留事实，不改写为新请求；作为风格来源的参考图存档不等于实际传入了图片。

历史兼容draw路线若使用远端URL，只冻结URL字符串，不承诺远端图片字节已固定，也不把它描述为本地输入图快照。并发准备使用专用锁，每次实际请求获得独立ID；这些执行信息只留内部证据，不加入模型提示词。

## 禁止冒充

以下不能冒充正式图片：

- 本地擦字。
- inpaint 或本地修补。
- HTML/canvas/SVG 渲染。
- 浏览器截图。
- source replay。
- fixture。
- copied source render。
- 复制旧图冒充新图。
- 只有图片文件，没有 packet、batch、对应路线 evidence 和 result 记录。

## 主控检查

主控大模型在提交用户确认前检查：

- 图片是否真实来自所选模式允许的正式路线：`codex_image_gen`直接内置或有证据的原生备用，或`openai_image_api` / 精确`gpt-image-2.5`；不同路线证据不混记。
- 每张 result 是否有 `image_generation_route`、对应结果 ID、对应 evidence path、`image_sha256` 和 batch 记录。
- 中转 API 路线同组多张图片是否按并发方式调用。
- 新阶段2结果是否统一保留原始像素与字节；历史postprocess的原始输出及canonical输出是否仍可追溯，未被改写成新图证据。
- 试样是否先于剩余页面供用户确认。
- 已选封面候选是否在质量通过后直接转正，且未进入阶段2B重复生图。
- 试样 promotion 是否保留原 trial result、trial image 和 evidence。
- 中文文字是否可读。
- 页面主题是否明确。
- 风格是否统一。
- 阶段2正式图是否记录 `1672x941` 目标、`1600x900` 优先底线、容差、`meets_target_size`、`meets_preferred_size` 和必要 `size_warnings`；低于优先底线时是否清楚记录风险。
- 实际图片相对16:9的比例偏差是否在2%以内（包含边界），四个比例字段是否与真实宽高一致；比例通过不代替清晰度与文字验收。
- 新图是否存在缩放、裁切、补边或重新编码；存在则不能作为原始正式图放行。PDF只改变页面放置尺寸，嵌入图像仍保留原始像素；旧处理记录保留事实，不自动重制旧课件。
- 信息层级是否清楚。
- 是否需要返工。
